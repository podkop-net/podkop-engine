# Возможности и опции

[English](FEATURES.md)

Что podkop-engine добавляет к sing-box из того, что настраивается: параметры
`/etc/config/sing-box`, окружение init-скрипта, опции JSON-конфигурации sing-box и инструменты
командной строки. Исправления и изменения, которые настраивать не нужно, — в
[CHANGELOG.ru.md](../CHANGELOG.ru.md), каждый патч — в [PATCHES.md](PATCHES.md).

«С rN» — выпуск podkop-engine. Всё здесь относится к линии 1.14 (`v1.14.4-r27`). Линия 1.13 больше
не собирается (последний выпуск — `v1.13.21-r18`); в линии 1.12 только патчи REALITY и uTLS. У линии
1.14 не было r3 и r4: то, что в них появилось, пришло на 1.14 в r5. sing-box без этих патчей
отвергает опции JSON ниже (например, `json: unknown field …`); программа, которая пишет конфигурацию для
разных движков, сначала смотрит [строку Features](#строка-features).

## Пакет на OpenWrt

Ставится один из двух пакетов. В `podkop-engine` — выходы, которые пишет podkop: direct, socks,
shadowsocks, trojan, vless, hysteria2, tuic, selector, urltest, http (с r15) и block (с r19).
`podkop-engine-full` добавляет vmess, snell, tor, ssh, shadowtls, anytls, hysteria и naive
(NaiveProxy — только на части архитектур). Входы в обоих: tproxy, direct, mixed. Выход из
`podkop-engine-full` в `podkop-engine` не проходит `sing-box check` с ошибкой «… not included in this
build (podkop_slim), install podkop-engine-full». Ни в одном пакете нет других входов (tun, socks,
http …), DNS-серверов `quic` и `h3`, служб api и ssm-api: с ними ошибка — «… not included in this
build (podkop_slim)». Выбор и смена пакета: [INSTALL.ru.md](INSTALL.ru.md).

### Параметры /etc/config/sing-box

Раздел `sing-box.main`. Параметры пакета sing-box из OpenWrt (`enabled`, `user`, `conffile`,
`workdir`, `ifaces`) работают как там. При обновлении `dns_fallback`, `urltest_download_check`,
`urltest_download_url` и `liveness` дописываются со значениями по умолчанию, если их нет; заданные
значения не меняются.

| Параметр | По умолчанию | Что делает | С |
|---|---|---|---|
| `dns_fallback` | `1` | Если установлен podkop: за DNS-сервер, к которому sing-box ходит напрямую через WAN, при его отказе отвечает [DNS провайдера](#резервный-dns) | r4 (1.14: r5) |
| `urltest_download_check` | `1` | [Проверка загрузкой](#проверка-загрузкой) перед переключением группы urltest | r8 |
| `urltest_download_url` | `https://speed.cloudflare.com/__down?bytes=65536` | Её адрес: `http://` или `https://` без пробелов; с r14 другое значение пропускается со строкой в журнале, и проверки нет | r8 |
| `memory_limit` | не задан: [автоматически](#лимит-памяти) | `off` или размер в MiB либо GiB (`64MiB`, `1GiB`, не больше 7 цифр), передаётся как `GOMEMLIMIT`; с r14 другое значение пропускается со строкой в журнале | r9 |
| `failsafe` | не задан: включён | `0`, `off`, `false`, `no` или `disabled` выключают [службу failsafe](#failsafe-и-самопроверка), а с ней и самопроверку | r12 (служба — с r4; 1.14: r5) |
| `liveness` | `1` | Самопроверка; выключается теми же значениями | r13 |

```sh
uci set sing-box.main.urltest_download_check=0
uci commit sing-box; service podkop restart     # без podkop: service sing-box restart
                                                # failsafe, liveness: service podkop-engine restart
```

`dns_fallback`, `failsafe` и `liveness` действуют, только если установлен podkop.

Без параметров init-скрипт ещё задаёт: 65536 открытых файлов, 15 с на остановку, серию падений
считает по промежуткам меньше 10 минут (`respawn 600 5 5`), в журнал не пишет коды цветов.

### Окружение sing-box

Эти переменные передаёт init-скрипт; программа, которая запускает sing-box сама, может задать их.

| Переменная | Что ставит init-скрипт | Действие | С |
|---|---|---|---|
| `SING_BOX_DNS_FALLBACK` | `ubus`, если установлен podkop и включён `dns_fallback` | Любое непустое значение включает резервный DNS | r4 (1.14: r5) |
| `SING_BOX_URLTEST_DOWNLOAD_URL` | `urltest_download_url`, если включён `urltest_download_check` | Адрес проверки загрузкой у группы urltest без `download_url` | r8 |
| `SING_BOX_RULESET_RECOVERED_HOOK` | `/usr/libexec/podkop-engine/lists-recovered`, если установлен podkop | Команда shell, которая выполняется, когда remote rule-set, не скачавшиеся при старте, пришли (один запуск на наборы, пришедшие в пределах 5 с друг от друга, ещё один — на пришедшие позже); их теги через запятую — в `SING_BOX_RULESET_TAGS` | r2 |
| `GOMEMLIMIT` | из `memory_limit` | Лимит памяти Go вместо автоматического | r9 |
| `SING_BOX_UTLS_FALLBACK` | — | Любое непустое значение включает [автосмену отпечатка uTLS](#автосмена-отпечатка-utls) для конфигурации без `experimental.utls_fallback` | r13 (любое значение — с r17) |
| `SING_BOX_RULE_SET_START_EMPTY` | — | Remote rule-set, которого нет в кэше, сразу стартует пустым и скачивается в фоне, старт его не ждёт (задаёт podkop-experimental) | r15 |

### Старт без списков

Если remote rule-set при старте не скачивается (WAN ещё не поднялся, неверное время, первый узел
urltest мёртв), sing-box стартует с пустым списком и пробует снова через 5, 10 и 20 с, дальше раз в
30 с, а не завершается с `FATAL … initial rule-set`. Когда списки пришли, хук запускает
`podkop list_update`, чтобы догрузились и списки самого podkop. Список, который есть в кэше,
берётся из кэша. С r2.

### Лимит памяти

По умолчанию sing-box держит лимит памяти Go равным тому, что занимает Go, плюс тому, что система ещё
может дать (`MemAvailable` или остаток до лимита cgroup), и пересчитывает его после каждой сборки
мусора: когда памяти мало, сборщик срабатывает раньше OOM-killer. При старте в журнале —
`memory limit <N>, following the available memory`. `memory_limit`, `GOMEMLIMIT` или
`experimental.debug.memory_limit` заменяют автоматический лимит. С r9.

### Failsafe и самопроверка

Служба `/etc/init.d/podkop-engine` следит за procd. Когда sing-box падает раз за разом и procd
сдаётся, она выполняет `/etc/init.d/podkop stop`: dnsmasq возвращается к обычным серверам, сеть
работает без прокси. Причина и память роутера пишутся в журнал и в `/etc/sing-box/failsafe.last`;
снова запустить podkop — `service podkop start`. С r4 (1.14: r5).

Самопроверка (с r13) раз в 20 с спрашивает у sing-box проверочное имя podkop через `127.0.0.42`.
После трёх запросов подряд без ответа (49–72 с) она завершает процесс; procd запускает его заново, и
это считается падением. Молчание считается только у процесса, который уже отвечал адресом FakeIP;
опросы во время `podkop list_update` и пока запрос не доставляет сам роутер (таблица соединений заполнена на
95 %, нет ответа на собственный ping) не считаются. После завершения в журнале остаётся
`has not answered DNS on 127.0.0.42 for N s`.

## Выходы и транспорты

### Транспорт XHTTP

Клиент транспорта XHTTP (SplitHTTP) из Xray, `"transport": {"type": "xhttp"}`, для любого
выхода с транспортом V2Ray: vless и trojan, в `podkop-engine-full` ещё vmess.
Имена полей — как в sing-box-extended; диапазон пишется `"100-1000"`, `"30"`, числом или
`{"from": 100, "to": 1000}`; неизвестное поле не проходит `sing-box check`. Имя в Features —
`transport.xhttp`. С r11.

```json
"transport": { "type": "xhttp", "mode": "auto", "host": "example.com", "path": "/api/" }
```

| Поле | По умолчанию | Замечания |
|---|---|---|
| `mode` | `auto` | `packet-up`, `stream-up`, `stream-one`; `auto` — это `stream-one` с REALITY (`stream-up` при `download`), иначе `packet-up` |
| `host`, `path`, `headers` | — | `headers` не может задавать `Host`, `Upgrade`, `Transfer-Encoding`, `Connection` и `Content-Length` |
| `x_padding_bytes` | `100-1000` | не 0, не больше 65536 |
| `uplink_http_method` | `POST` | `GET` — только в `packet-up` |
| `sc_max_each_post_bytes` | `1000000`; `4096`, если `uplink_data_placement` — `header` или `cookie` | мегабайт Xray не помещается в 8 КиБ заголовков, которые принимает сервер |
| `sc_min_posts_interval_ms` | `30` | |
| `xmux` | если в нём ничего не задано: `max_connections` 3, `h_max_request_times` 600-900, `h_max_reusable_secs` 1800-3000 | `max_connections` и `max_concurrency` вместе нельзя; ещё `c_max_reuse_times`, `h_keep_alive_period` |
| `download` | — | отдельный сервер для скачивания: `server`, `server_port` (обязателен), `tls`, `detour` и поля выше, кроме `mode`; не вместе со `stream-one` |

Остальные поля Xray называются так же (`x_padding_*`, `session_*`, `seq_*`, `uplink_data_*`,
`uplink_chunk_size`, `no_grpc_header`); серверные поля принимаются и не используются. VLESS `flow`
поверх XHTTP требует [шифрования VLESS](#шифрование-vless). Нет серверной стороны, `finalmask` и
Browser Dialer. Без аппаратного AES шифр важнее всего: MT7621 (r11, 50 МБ) — 1,9 МБ/с с `utls`
`chrome` (первым предлагает AES-GCM), 3,26 МБ/с без `utls` (ChaCha20), 3,75 МБ/с без прокси.

### Шифрование VLESS

`encryption` у выхода vless — сторона клиента шифрования VLESS (VLESS Encryption) из Xray: обмен
ключами ML-KEM-768 и X25519 и шифрование всего потока до сервера; сервер, у которого задан
`decryption`, клиента без него не принимает. Значение — строка клиента Xray, как её печатает
`xray vlessenc` и пишут в ссылку панели:
`mlkem768x25519plus.<native|xorpub|random>.<1rtt|0rtt>[.<дополнение>…].<ключ>[.<ключ>…]`. Пустое
значение или `none` — без шифрования. Строка, которую не принял бы Xray, — ошибка при старте. С r14.

```json
{ "type": "vless", "server": "192.0.2.1", "server_port": 443, "uuid": "…", "flow": "xtls-rprx-vision",
  "encryption": "mlkem768x25519plus.native.0rtt.<ключ>", "tls": { "enabled": true, "server_name": "example.com" } }
```

`0rtt` отправляет данные сразу, по билету первого обмена, `1rtt` делает полный обмен на каждом
соединении. Ключ — base64url от 32 байт (X25519) или 1184 байт (ML-KEM-768); несколько ключей — для
цепочки; паузы сегментов дополнения (`100-111-1111`) — не больше 10 с в сумме. С `encryption`
`flow: xtls-rprx-vision` работает с любым транспортом и без TLS (сервер Xray принимает `flow` поверх
XHTTP только с шифрованием VLESS). Шифр — AES-GCM при аппаратном AES, иначе ChaCha20-Poly1305; молчащий сервер
завершает рукопожатие через 15 с. Стороны сервера нет; имени в строке `Features:` нет.

### tls.spoof с REALITY

Опции TLS `spoof` и `spoof_method` из sing-box 1.14 (и опция маршрута `tls_spoof`) перед настоящим
ClientHello отправляют поддельный, с именем из `spoof`, собранный так, чтобы сервер его отбросил
(`spoof_method`: `wrong-sequence` по умолчанию, `wrong-checksum`, `wrong-ack`, `wrong-md5`,
`wrong-timestamp`). Здесь они работают и с REALITY, где upstream их запрещает, а поддельный пакет
уходит тем же путём, что соединение (метка, интерфейс, адрес источника, TTL). С r13.

```json
"tls": { "enabled": true, "server_name": "example.com", "spoof": "allowed.example.net",
  "utls": { "enabled": true, "fingerprint": "chrome" }, "reality": { "enabled": true, "public_key": "…", "short_id": "…" } }
```

Ограничения: нужен root (`CAP_NET_RAW`, `CAP_NET_ADMIN`). Только соединение прямо к серверу TLS:
`detour` к прокси-выходу — ошибка конфигурации (к `direct` — работает); не вместе с
`tcp_fast_open` и транспортом с несколькими потоками в соединении. Для `wrong-timestamp` нужны
метки времени TCP, для `wrong-ack` — ядро сервера 6.7 или стабильный выпуск с декабря 2023 года. В `spoof` —
имя, которое фильтр пропускает (из его белого списка); имя не из списка не помогло. У одного провайдера (2026-10-08), который обрывает соединение после 25 пакетов, если в
первом ClientHello нет имени из белого списка, загрузка 200 КБ без `spoof` не прошла в 8 запусках из
8, а с ним прошла в 21 из 21 (всеми способами, кроме `wrong-checksum`, который не помог).

### Автосмена отпечатка uTLS

По умолчанию выключена; включается для всей конфигурации так:

```json
"experimental": { "utls_fallback": { "enabled": true } }
```

Тогда клиент TLS или REALITY с отпечатком uTLS следит за своим рукопожатием. Если ClientHello не
подтверждён после двух повторов (около секунды на пути с задержкой 50 мс, не дольше 5 с) и сервер
ничего не прислал, соединение бросается и устанавливается заново: с тем же пунктом ещё раз, если
он первый или уже работал на этом пути, иначе — со следующим:

1. отпечаток из конфига без ключа X25519MLKEM768 (у `edge`, `ios`, `qq`, `360`, `android` его нет,
   они идут как есть);
2. `firefox` с ключом;
3. отпечаток из конфига как есть.

Первый пункт, на который сервер ответил, запоминается для сервера на сутки — в `cache.db`, если кэш
включён. Сервер REALITY на Xray-core 26.9.8 и новее отвечает на ClientHello без ключа как
постороннему, и это сразу переводит на следующий пункт. Если не ответил ни один пункт, автосмена
отдыхает 30 с (каждый раз вдвое дольше, до 10 минут). Список `fingerprints` в разделе принимается и
не используется. Имя в Features — `tls.utls-fallback`. С r13; этот порядок и `cache.db` — с r17.

Ограничения: только Linux; только соединение TCP, которое sing-box открывает сам (не через `detour`
к прокси-выходу; не hysteria2, tuic, shadowtls; не вместе с `tcp_fast_open`, kTLS и ECH из DNS);
замечается только ClientHello, отброшенный молча. Пока первое соединение к серверу пробует пункты,
остальные ждут его до 5 с. На пути, который замораживает пачки ClientHello `chrome` (r17, REALITY,
Xray 26.6.27), из 20 одновременных запросов с одним `chrome` не прошёл ни один, с автосменой — 18–20.

### fragment и record_fragment с REALITY

Опции TLS `fragment` (ClientHello несколькими сегментами TCP) и `record_fragment` (несколькими
записями TLS) действуют и у клиента REALITY; upstream там их принимает и ничего не делает. Сервер
собирает тот же ClientHello, и проверка REALITY проходит. podkop-experimental предлагает
`"record_fragment": true` против заморозки по отпечатку: на таком пути без него прошло 0
подключений из 15, с ним — 15 из 15. С r24.

### Выход block

`block` есть и в `podkop-engine` (с r19) и может быть [резервным выходом urltest](#резервные-выходы)
(с r20). Соединение, которое он отклонил, пишется в журнал на уровне debug, как отклонённое
действием `reject`; собственная строка выхода `blocked connection to …` остаётся на уровне info.

## Группы urltest

Опции, которые сборка добавляет выходу типа `urltest`:

| Опция | По умолчанию | С |
|---|---|---|
| `fallbacks` | — | r10; группа из одних резервных — с r20 |
| `download_url` | `SING_BOX_URLTEST_DOWNLOAD_URL` | r10 |
| `urls` | `url` | r24 |
| `mode` | `fastest` | r24 |
| `loss_url` | — (обязателен для `loss` и `balance`) | r24 |
| `loss_interval` | `30m` (не меньше `1m`) | r24 |
| `loss_threshold` | `1` (процент) | r24 |
| `balance_size` | `3` (от 1 до 16) | r24 |
| `balance_idle` | `5m` | r24 |

### Резервные выходы

```json
{ "type": "urltest", "tag": "auto", "outbounds": ["vps-1", "vps-2"], "fallbacks": ["backup-vps", "block-out"] }
```

Пока хоть один из `outbounds` проходит проверку, группа выбирает среди них как обычно, даже если
резервный быстрее. Когда не проходит ни один (нет результата или встала проверка загрузкой), берётся
первый по порядку резервный, у которого есть результат, и группа возвращается, как только основной
снова проходит проверку. Резервный `block` не проверяется и отказывает сразу; пока он выбран, раунды
идут через 30 с, затем каждый раз вдвое позже, но не реже интервала. До конца первого раунда после
старта или замены на ходу резервные не берутся. `outbounds` можно не задавать (с r20). Тег не может
быть в обоих списках. В Clash API `/proxies` резервные стоят в конце `all`, а с r21 перечислены ещё
и в `fallbacks`. Имя в Features — `urltest.fallbacks`.

### Проверка загрузкой

Сервер за DPI, который замораживает соединение после ~16 КБ, проходит URL-проверку в несколько сотен
байт. Поэтому перед переключением на участника группа скачивает через него 64 КиБ; участник, у
которого загрузка встала, пропускается до следующего результата его проверки. Выбранный участник не
проверяется; если других нет, берётся и замороженный. Цена — 64 КиБ на переключение. `download_url`
группы главнее `urltest_download_url`: `""` выключает проверку, ссылка включает её даже при
`urltest_download_check=0`; тело должно быть не меньше 64 КиБ. Имя в Features —
`urltest.download_url`. С r8; опция группы — с r10.

### Несколько URL, медиана, повтор

```json
{ "type": "urltest", "tag": "auto", "outbounds": ["a", "b"],
  "urls": ["https://check-1.example.com/generate_204", "https://check-2.example.com/generate_204"] }
```

Один адрес на раунд, по очереди; очередь считается по часам, так что все группы процесса в одном
раунде проверяют одним адресом. Задержка участника — медиана последних раундов (их столько, сколько
адресов). Участник, не ответивший адресу раунда, проверяется ещё раз адресом, который в прошлый раз
через него отвечал: недоступен он, когда не ответили два адреса. При `urls` поле `url` не
используется. С r24.

Проверки всех групп идут одним проверяющим процесса (с r24): проверка, которую уже ждёт другая
группа, не повторяется, а проверки через один и тот же первый сервер начинаются с разницей в 2 с.
Одновременно в процессе идёт не больше 4 URL-проверок (с r20; ожидание очереди в таймаут не входит)
и одна проба потерь.

### Режимы loss и balance

```json
{ "type": "urltest", "tag": "auto", "outbounds": ["a", "b", "c"], "mode": "balance",
  "loss_url": "https://speed.cloudflare.com/__down?bytes=1048576", "balance_size": 2 }
```

- `loss`: задержки сравниваются с поправкой на потери участников. Раз в `loss_interval` участник в
  работе и три лучших других скачивают 256 КиБ с `loss_url`; участник, на которого группа
  переключилась бы без свежего счёта, сначала скачивает 1 МиБ в фоне. Потери, которые видны у всех
  посчитанных участников, — потери линии и ничего не двигают. На стенде страница стоила
  59 + 4,85·RTT + p·(155 + 1,2·RTT) мс (RTT в мс, p — потери в процентах): участник на 20 мс с
  потерями 0,8 % стоит столько же, сколько чистый на 50 мс (участник по TCP; участник hysteria2 или
  tuic на коротких RTT платит намного меньше: 1 % стоит ×1,03 при 20 мс, ×1,44 при 100 мс).
- `balance`: соединения распределяются по адресу источника между не более чем `balance_size`
  лучшими участниками (в пределах `tolerance`, потери не выше `loss_threshold`). Устройство остаётся
  на своём участнике, уходит сразу, когда тот упал, и распределяется заново после `balance_idle` без
  соединений.

`loss_url` должен отдавать не меньше 1 МиБ. Проба считает потерянные сегменты своего TCP-соединения
(пакетный сокет, нужен root). Участник hysteria2 или tuic считается по пакетам своего соединения QUIC
(с r27), если `loss_url` понимает параметр `bytes` или HTTP Range; иначе он идёт по задержке, как и
участник на мультиплексированном транспорте. Clash API `/proxies` показывает `mode`, `balance` и
`loss` каждого участника за 1–24 часа. С r24.

## DNS

### Резервный DNS

Включается переменной `SING_BOX_DNS_FALLBACK` (параметр `dns_fallback`, если установлен podkop).
Касается сервера, к которому sing-box ходит обычным сокетом (без `detour` или с `detour` на
`direct`; без `bind_interface`, `routing_mark`, адреса привязки, netns), по публичному адресу или
доменному имени; серверы за прокси и группами, VPN-секции podkop, локальные и частные резолверы не
затрагиваются. С r4 (1.14: r5).

- Нет ответа за 3,5 с, отказ или сброс соединения, ошибка TLS или HTTP, SERVFAIL — запрос задаётся
  DNS провайдера (netifd через ubus); его ответы живут не дольше 60 с. После двух отказов подряд (не
  SERVFAIL) сервер отставляется и проверяется копией запроса через 30 с, дальше реже, до раза в 5
  минут. Если провайдер не ответил два раза подряд, резерв для этого сервера выключается на минуту.
- Какие серверы провайдера: того устройства, к которому sing-box привязывает сокеты
  (`auto_detect_interface`, `default_interface`); без привязки (с r16) — всех аплинков с маршрутом
  по умолчанию, кроме туннелей, каждый через свой аплинк. С mwan3 такому сокету нужно правило
  `ip rule` раньше правил mwan3, которое отправляет его в основную таблицу; podkop-experimental его
  ставит.
- В журнале на уровне warn (с r14): `server <tag> falls back to provider DNS when it fails` или
  `no provider DNS fallback for server <tag>: <reason>`.

### Группа DNS-серверов и DNS провайдера

Два типа DNS-сервера (с r21):

```json
"servers": [
  { "type": "https", "tag": "dns-1", "server": "dns.example.com" },
  { "type": "provider", "tag": "dns-2" },
  { "type": "udp", "tag": "dns-3", "server": "192.0.2.53" },
  { "type": "group", "tag": "dns-server", "servers": ["dns-1", "dns-2", "dns-3"], "strategy": "order" }
]
```

- `provider` (без опций) спрашивает DNS провайдера так же, как резервный DNS; если роутер их сейчас
  не знает, запрос сразу получает ошибку.
- `group` спрашивает свои `servers` (кроме `group`, `fakeip` и `hosts`). `strategy`: `order` (по
  умолчанию) — по порядку списка; `fastest` — сначала самый быстрый по сглаженному времени, остальные
  измеряются копиями запросов в фоне. Ответ — это NOERROR и NXDOMAIN; с другим кодом спрашивается
  следующий.
- Попытка ждёт 4 сглаженных времени участника, от 1,5 до 3 с (3 с, пока он не измерен); у последней —
  только срок запроса. После таймаута, если впереди больше одного участника, остальные спрашиваются
  сразу все (с r25). После двух отказов подряд участник отставляется и проверяется через 30 с, дальше
  до раза в 5 минут.
- При включённом резервном DNS группа без `provider`, в которой хотя бы один участник получил бы
  резервный DNS сам по себе, спрашивает провайдера, когда отказали все.

Закрытый стенд, три сервера по 80, 20 и 40 мс: `order` — медиана 82 мс, `fastest` — 22 мс, копии —
0,6 % запросов.

### ipv6_if_no_ipv4

```json
"dns": { "strategy": "ipv4_only", "ipv6_if_no_ipv4": true }
```

Со стратегией `ipv4_only` запрос AAAA уходит, если запрос A того же имени через тот же сервер
получил успешный ответ без записей A: сайт только с IPv6 открывается. Имя с адресом IPv4 по-прежнему
получает пустой ответ на AAAA, имена FakeIP не затронуты. Поиск адреса самим sing-box (сервер выхода,
действие `resolve`) и `ipv4_only` в правиле DNS тоже учитывают опцию. С выключенным кэшем DNS каждый
AAAA стоит лишнего запроса A. По умолчанию выключена; Go-бэкенд podkop-experimental её включает. С
r17.

## Списки (rule-set)

### Формат text

```json
{ "type": "remote", "tag": "my-list", "format": "text", "url": "https://example.com/domains.txt" }
```

Локальный или удалённый список простым текстом, запись на строку. Домен (с точкой или начинающийся
с `.` или `+.`) совпадает сам и с поддоменами (`domain_suffix`); адрес IP или подсеть — по
назначению (`ip_cidr`); `#` и `//` начинают комментарий. Остальные строки пропускаются; список без
единой записи (страница блокировки вместо списка) — ошибка. С r15.

### Резервные клиенты и пути загрузки

Две опции HTTP-клиента; ими пользуются remote rule-set, которые его называют:

```json
"http_clients": [
  { "tag": "via-proxy", "detour": "proxy-1" },
  { "tag": "lists", "fallback": ["via-proxy"] },
  { "tag": "lists-any", "outbounds": ["direct", "proxy-1", "proxy-2"] }
],
"route": { "rule_set": [
  { "type": "remote", "tag": "my-list", "format": "binary", "url": "https://example.com/list.srs", "http_client": "lists-any" }
] }
```

- `fallback` (с r25): теги клиентов из `http_clients`. Список, который не пришёл через свой клиент
  (ошибка, чужой ответ, 30 с без данных, не список), скачивается заново через каждый резервный по
  очереди, у каждого свои 30 с.
- `outbounds` (с r26): только у клиента из `http_clients`, не вместе с `detour` и `fallback`; пути,
  которыми идут его загрузки. Для хоста первым идёт путь, который принёс его прошлый файл, затем
  первый в списке, пути, о которых известно, что они работают (быстрые раньше), неизвестные и
  последними — не сумевшие для этого хоста. Следующий путь начинается рядом с идущими, если они 4 с
  без ответа или тело стоит 1 с (3 с после первого МиБ), не больше трёх сразу; берётся первый ответ,
  разобранный как список. Сроки — по 1200 загрузкам на клиента (Filogic 820, MT7621, x86): самый
  медленный ответ рабочего пути — 3,78 с, самая долгая пауза в теле — 0,94 с.

### Где лежат списки

Удалённый список хранится в своём файле рядом с файлом кэша, `<путь cache.db>.rule-sets/<тег>-<хэш>`,
а не внутри него (с r18); списки прошлого выпуска переносятся при старте, а откат на него скачивает
их заново. Ответ 304 записывает только время проверки (с r16). Список больше 50 МиБ отклоняется;
списки от 1 МиБ обновляются по одному.

## Снифферы: BitTorrent

Сниффер `bittorrent` (входит в набор действия `sniff` по умолчанию) узнаёт UDP-сокет
торрент-клиента. DHT (BEP 5) — новый сниффер пакетов: клиент шлёт DHT, uTP и UDP-трекер с одного
сокета, и его первый пакет, запрос DHT, решает протокол всего сокета. uTP опознаётся только по SYN,
как в Xray; из 200 000 случайных пакетов от 40 до 1400 байт ни один не принят ни за uTP, ни за DHT,
а туннель WireGuard не принимается за uTP (с r18). С r27.

```json
"rules": [ { "action": "sniff" }, { "protocol": "bittorrent", "outbound": "direct" } ]
```

## Программы, которые встраивают движок

Интерфейсы Go, которыми пользуется podkop-experimental; из `config.json` и командной строки они
недоступны.

### Замена выходов на ходу

```go
// package box (github.com/sagernet/sing-box)
func (s *Box) UpdateOutbounds(outbounds []option.Outbound, remove []string, limit int) (OutboundUpdate, error)
```

Строит и запускает новые выходы под их тегами в работающем sing-box и убирает теги из `remove`. Новые
соединения идут через новые объекты; прежние закрываются, когда в Clash API нет соединений через них,
не раньше чем через 2 минуты и не позже чем через сутки (более старое соединение через общий
транспорт — gRPC, HTTP/2, XHTTP, QUIC, multiplex — тогда обрывается). Заменённая группа urltest
передаёт свой выбор новой. Замена отвергается, если остающийся выход идёт через заменяемый или если
соединения ещё держат больше `limit` заменённых выходов (не групп; `0` — без предела); отвергнутая
замена ничего не меняет. `detour` (HTTP-клиента, DNS-сервера, загрузки XHTTP) находит свой выход по
тегу при каждом наборе. С r19.

### Детектор блокировок

При включённом файле кэша движок записывает по каждому серверу REALITY, остался ли без ответа каждый
ClientHello, сорвалось ли рукопожатие после ответа и не отверг ли сервер первого кандидата автосмены
как постороннего (Xray-core с 26.9.8), и отпечаток в работе (`adapter.CacheFile.LoadDetectOutcome`).
Соединения считают байты в обе стороны и знают, закончил ли поток удалённый конец; история
URL-проверок хранит последнюю неудачную проверку и последнюю проверку загрузкой. На соединения записи
не влияют. С r21. Ещё: `adapter.DNSGroupTransport`, `adapter.DNSProviderTransport` (r21).

## Инструменты

### sing-box tools decode-link

```sh
echo 'vless://…@example.com:443?type=xhttp&security=tls&…#name' | sing-box tools decode-link --compact
```

Печатает outbound для одной ссылки (из stdin или аргументом): код 0 и JSON, строки `warning: …` в
stderr; 2 и одна строка `error: …`, если ссылку использовать нельзя; 1 — всё остальное. Сообщения не
повторяют ссылку. Outbound строится кодом `sing-box check`, поэтому напечатанное этот бинарь примет.
Схемы: `vless`, `trojan`, `ss`, `socks` (и `socks4`, `socks4a`, `socks5`, `socks5h`), `hysteria2`/`hy2`, `tuic`, `http`/`https`; в
`podkop-engine-full` ещё `vmess`, `hysteria`, `anytls`, `naive+https`/`naive+quic`. Любая другая
опция — `sb.<путь>` (`sb.tls.record_fragment=1`). Имя в Features — `tools.decode-link`. С r11, все
протоколы — с r13. Все параметры: [LINKS.md](LINKS.md).

### Строка Features

```
$ sing-box version
sing-box version 1.14.4-pdk-r27
…
Features: urltest.fallbacks,urltest.download_url,transport.xhttp,tools.decode-link,tls.utls-fallback
```

Последняя строка `sing-box version` (с r11) называет то, что сборка добавляет и от чего может
зависеть конфиг или скрипт: `urltest.fallbacks` и `urltest.download_url` (сами опции — с r10),
`transport.xhttp`, `tools.decode-link`, а с r13 — `tls.utls-fallback`. Имя не удаляется и не меняет
смысла; без нужного имени podkop опцию не пишет. Опции без имени узнаются по версии (`-pdk-rN`).

Службы API нет ни в одном пакете. В `podkop-engine` нет ещё `sing-box tools networkquality`,
`sing-box tools stun` и `sing-box schema` (с r26); в `podkop-engine-full` эти три есть.

## Работает без настройки

Коротко; подробности — в [CHANGELOG.ru.md](../CHANGELOG.ru.md) и [PATCHES.md](PATCHES.md).

- REALITY и отпечатки uTLS — как у клиента Xray 26.9.9 (X25519MLKEM768, версия 26.3.27).
- DNS: свой сокет на каждый запрос UDP к серверу без прокси; DoH и DoT держатся при потерях.
- FakeIP: таблица в памяти, `cache.db` дописывается в фоне; после падения адреса не достаются другим
  доменам. Откат на прежний выпуск или обычный sing-box читает cache.db, но известные имена один раз получат
  новые адреса.
- urltest: участник, чьи соединения отказывают или молчат, проверяется сразу и оставляется.
- Списки — в компактных структурах; меньше памяти на соединение; паника сниффера стоит одного
  соединения. Отпечаток uTLS у hysteria, hysteria2 и tuic отбрасывается с предупреждением.
- REALITY: отпечатки `android` и `360` — ошибка конфигурации, `edge`, `ios` и `qq` — предупреждение
  (серверы Xray-core 26.9.8+ их отвергают); `short_id` длиннее 16 шестнадцатеричных цифр — ошибка.
